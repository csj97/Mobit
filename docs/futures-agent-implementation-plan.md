작성일: 2026-09-21. 최종 검토일: 2026-09-22. 상태: 단계별 구현 진행 중. 2026-09-22 사용자의 코드 작업 지시에 따라 기반 구현을 시작했다. SDK 추가·원격 DB 생성·배포는 수행하지 않았다.

R02/R03은 신규 지급 정책이다. 이미 사용자가 보유한 다른 거래소 자산이나 광고로 얻은 잔고를 0으로 되돌리라는 뜻이 아니다. 업데이트·마이그레이션 중 기존 자산은 보존한다.

현재 운영 범위는 국내 거래소의 KRW/BTC 마켓이며 USDT는 아직 없다. USDT 보상 정책 확정은 USDT 상품 연동 완료를 뜻하지 않는다. 과거 Supabase 선호는 필요 시 공용 시장 데이터·설정을 적재할 수 있다는 범위로만 남기며, 개인 거래 기록을 원격에 저장하는 전제는 제거한다.

계좌 내부에서 현물의 결제 자산을 매매하거나 증거금을 예약하는 것은 기존 거래 활동이다. 이를 계좌 간 이체 기능으로 확대하지 않는다. 같은 거래소의 현물과 선물도 서로 독립된 계좌다.

## 2. 첫 버전과 후속 버전

### v1: 간이 선물 모의거래

아래는 확정 정책을 구현하기 위한 권고 범위다. 최초 선물 거래소·상품·레버리지 상한은 가격 자료 검증 후 정하며, 현재 국내 KRW/BTC 지원 범위를 이미 USDT로 확장했다고 해석하지 않는다.

- 거래소별 현물/선물 선택, 독립 계좌, 광고 충전.
- 검증 가능한 거래소의 USDT 선형 무기한 상품부터 활성화. 구조는 N개를 수용한다.
- 롱/숏, 제한된 레버리지, 신규 진입·전량 종료.
- 포지션별 투입 증거금 대비 손익률 -100% 이하에서 청산하는 명시적 모의 정책.
- 수수료·확정 펀딩 이력·청산 원장·재접속 정산·거래소별 PNL.
- 실제 cross/isolated 선택 UI는 미노출 또는 준비 중. cross를 선택하게 한 뒤 몰래 -100%에서 청산하지 않는다.
- 추가 진입·부분 종료·자동 TP/SL·지정가·증거금 추가·레버리지 변경은 후속 범위로 둔다.

### v2: 실제 의미의 cross/isolated

- isolated: 해당 포지션 담보와 유지증거금 조건으로 판단한다.
- cross: 같은 거래소·같은 선물 계좌·같은 담보 통화의 적격 자본, 다른 cross 포지션의 손익, 주문 예약액, 비용을 함께 계산한다.
- cross는 특정 포지션 손익률이 -100% 아래여도 계좌 담보가 충분하면 유지될 수 있다. 반대로 유지증거금 조건을 만족하지 못하면 개별 포지션이 -100%에 이르기 전에도 청산될 수 있다.
- cross의 공유 범위에 다른 거래소·현물 계좌·다른 isolated 포지션의 전용 담보를 포함하지 않는다.
- 단순히 `if cross { 청산 생략 }`으로 구현하지 않는다. 무제한 손실 허용이 아니다.
- 실제 거래소별 유지증거금 구간, 비용, 청산 순서와 모드 전환 제한을 조사한 뒤 적용한다.
- cross 재접속 정산은 계좌의 여러 종목을 같은 시각 기준으로 재생해야 한다. 서로 다른 시각에 발생한 각 종목의 봉 최저가를 합쳐 가상의 계좌 최저 자본을 만들지 않는다. 동시 가격 경로가 복원되지 않으면 별도 근사 정책과 검증 자료가 필요하며, v1의 독립 포지션 정산을 그대로 재사용해 정확하다고 주장하지 않는다.
- v1 포지션에 새 규칙을 소급 적용하지 않는다. 규칙 버전을 유지하고, 초기에는 포지션 보유 중 모드 전환을 허용하지 않는 방향을 검토한다.

실제 cross 설명의 근거: [Bybit USDT 계약 FAQ](https://www.bybit.com/en/help-center/article/FAQ-USDT-Perpetual-and-Expiry-Contracts). 특정 거래소의 수치·알고리즘을 모든 거래소에 일반화하지 않는다.

### 즉시 드러난 우선 수정점

1. 시드 함수가 전역 선택 거래소에 의존한다. 최초 지급은 선택 상태와 무관하게 업비트 현물에 귀속되어야 한다.
2. 첫 실행 플래그를 잔고 저장 전에 바꾼다. 지급 사건·잔고·완료 상태의 일관성을 검토한다.
3. 광고가 닫힌 사실만으로 보상 지급을 호출하는 경로가 있다. 보상 획득과 닫힘은 구분해야 한다.
4. 광고 보상이 완료될 때 전역 현재 계좌를 읽으므로 시작 당시의 대상 계좌를 고정해야 한다.
5. 충전 로직이 두 View에 중복되어 있어 계좌 분리 시 한쪽만 바뀌는 위험이 있다.

## 4. 계좌·상품·원장 설계

### 계좌 경계

```text
AccountID = 현재 로컬 데이터 영역 안의 거래소 + 현물/선물 + 기준 결제 통화
InstrumentID = 거래소 + 상품 종류 + 원본 심볼 + 결제 통화
PositionID = 고유 ID, AccountID 및 InstrumentID에 귀속
```

현물의 기존 KRW 잔고·BTC 결제 자산 구조를 통화마다 새로운 무료 계좌를 생성하는 방식으로 바꾸지 않는다. 선물 USDT 잔고를 현물 KRW Double 필드에 넣지 않는다. 새로운 식별자는 선물 및 통합 경계부터 도입하고 기존 `ExchangePairID` 전체 이관은 필요한 경우에만 수행한다.

### 최소 저장 모델

| 모델 | 필수 내용 |
|---|---|
| 계좌 | AccountID, 통화, 가용 잔고, 저장 revision, 지급·충전 사건 참조 |
| 주문 | requestID, AccountID, InstrumentID, 방향, 수량, 레버리지, 접수·체결 시각, 가격 근거, 상태 |
| 포지션 | PositionID, 계좌·상품, 방향, 체결 레버리지, 진입가, 실제 수량·명목금액, 최초 증거금, 남은 담보, 상태, 규칙 버전 |

원장 종류는 최소 `initialGrant`, `adReward`, `open`, `close`, `tradingFee`, `funding`, `liquidation`을 구분한다. 여러 레코드로 비용을 분리할 때 실제 잔액을 두 번 차감하지 않는다. 이체 사건 종류는 추가하지 않는다.

모든 신규 시각은 UTC 기준 숫자 timestamp로 저장하고 연도는 표시할 때 변환한다. 연도 없는 기존 PNL 기록을 임의의 연도로 채우지 않는다.

## 5. 초기 자금·광고 충전 규칙

### 초기 자금

| 계좌 | 신규 초기 지급 |
|---|---:|
| 업비트 현물 KRW | 최초 한 번 1,000,000 KRW |
| 업비트 선물 | 지원 시 0 |
| 다른 거래소 현물 | 0 |
| 다른 거래소 선물 | 0 |

- 잔고 0, 로컬 키 누락, 디코딩 실패, 통신 실패를 무조건 최초 지급으로 해석하지 않는다. 새 로컬 데이터 영역과 기존 저장 손상을 구분한다.
- 기존 설치의 시드·잔고가 확인되면 지급 완료로 이관하고 기존 금액을 보존한다.
- 앱 업데이트·계좌 생성·계좌 전환·재시도로 재지급하지 않는다.
- 투자내역 초기화는 최초 지급 자격을 되살리지 않는다. 기존 초기화 범위 변경은 별도 정책으로 다룬다.
- 최초 지급과 광고 중복 방지의 범위는 현재 로컬 데이터 영역이다. 앱 삭제·기기 변경 후에는 이전 기록을 복구하지 않으며, 깨끗한 설치는 신규 로컬 이용 흐름으로 취급한다. 재설치 전 사용자를 추적해 지급을 막는 로그인·Keychain 영구 식별자·서버 계정을 추가하지 않는다. 앱 내 초기화와 업데이트는 앱 삭제와 구분하고 기존 지급 완료 정보를 보존한다.

### 광고 충전 흐름

```text
대상 계좌·보상 금액 표시
  → 계좌·금액·통화·정책 버전·rewardClaimID 고정
  → 광고 로드·노출
  → 보상 획득 콜백 수신
  → 지급 대상 계좌의 필요한 과거 정산 확인
  → 보상 사건·잔고를 원자적으로 저장
  → 충전 완료 표시
```

- 광고 닫힘은 화면 정리, `userDidEarnRewardHandler`는 보상 획득의 근거로 사용한다.
- 조기 닫기, 로드 실패, 노출 실패는 보상으로 처리하지 않는다.
- 보상 획득 이후 지급 저장이 실패하면 재시도 가능한 권리를 보존한다. 광고를 다시 보게 해서 이미 획득한 보상을 대체하지 않는다.
- 완료 안내는 실제 로컬 저장 성공 뒤에 표시한다. 정산·저장 대기는 충전 완료와 구분한다.
- 광고 요청이 중첩되어 싱글톤 completion이 덮어써지지 않게 한다. 동시 표시를 막고 완료·실패 후 참조를 정리한다.
- 계좌 전환 후 콜백이 와도 시작 당시 계좌에 지급한다. ViewController가 해제되더라도 지급 처리는 화면 수명에 매달리지 않게 한다.
- 콜백 중복·저장 재시도·앱 재실행은 같은 rewardClaimID로 한 번만 반영한다. 단말이 생성한 ID만으로 광고 위조까지 방지되는 것은 아니다.
- 기존 KRW 광고 보상은 코드상 1회 10,000,000 KRW다. 요청 없이 이 금액을 바꾸지 않는다.
- USDT 광고 보상은 1회 1,000 USDT로 확정한다. 현재 KRW 광고 보상 10,000,000 KRW와 통화별 정책으로 구분하고 자동 환산하지 않는다. USDT 마켓이 없는 현재 화면에는 가짜 계좌/마켓을 노출하지 않으며 지원 계좌가 생기면 이 정책을 적용한다. 별도 BTC 직접 지급 정책은 만들지 않고 기존 현물 KRW 충전·BTC 매수 흐름을 유지한다. 새로운 회수 제한·대기 시간은 확정되지 않았으므로 임의로 도입하지 않는다.
- 광고 보상·최초 지급은 자본 유입으로 기록한다. 매매 PNL과 성과 수익으로 계산하지 않는다.
- 광고로 늘어난 잔고가 이미 과거에 청산된 포지션을 소급해서 살리지 않는다. 보상 획득 시각과 실제 기록 시각을 구분한다.
- v1 광고 충전은 가용 잔고 증가이며 열린 포지션 담보의 자동 증액이 아니다. v2 cross에서 영향이 생기면 획득 시각 이후 계좌 자본으로만 적용한다.

광고 콜백 근거: [Google AdMob iOS Rewarded Ads](https://developers.google.com/admob/ios/rewarded). 광고 획득/닫힘 콜백 순서는 미디에이션에 따라 다를 수 있으므로 닫힘만을 보상 조건으로 쓰지 않는다. QA는 테스트 광고를 사용한다. 서버 검증(SSV)은 후속 부정 지급 방어로 검토할 수 있지만, 이번 안에 상시 서버를 자동 추가하지 않는다.

## 6. v1 -100% 청산: 계산 계약 제안

사용자가 확정한 것은 -100% 청산을 우선 구현할 수 있다는 점이다. 아래 비용 포함 방식은 모호함을 없애기 위한 제안으로, 엔진 구현 전 규칙표에 확정한다. 실제 거래소 유지증거금 청산 모형과 같다고 표시하지 않는다.

### 용어와 수식

```text
M: 최초 투입 증거금(양수, v1에서 고정)
Q: 기초자산 수량
P0: 모의 진입 체결가
P: Mark Price
s: 롱 +1, 숏 -1
F: 현재까지 확정 펀딩 순수취액(지급이면 음수)
FeePaid: 포지션 담보에서 이미 낸 거래 수수료

미실현 매매손익 U = s × Q × (P - P0)
남은 담보 C = M + F - FeePaid
포지션 자본 E = C + U
청산 기준 손익률 = (U + F - FeePaid) / M × 100
청산 조건 = E ≤ 0, 즉 청산 기준 손익률 ≤ -100%
```

권고 비용 처리: 진입 시 가용 잔고에서 M을 예약하고, 진입 수수료는 그 담보 안에서 차감한다. 거래 화면에 총 투입액과 비용 차감 후 담보를 구분한다. 최초 유효 담보가 0 이하인 주문은 거절한다. 이 방식을 채택하면 수수료를 가용 잔고에서도 한 번 더 빼지 않는다. 종료 전 예상 종료 수수료는 별도 추정이며 이미 낸 비용에 넣지 않는다.

남은 담보가 일정한 구간에서의 간이 임계 가격은 롱 `P0 - C/Q`, 숏 `P0 + C/Q`다. 펀딩·비용 사건 후 C를 갱신하고 즉시 청산 조건을 재검사한다. 갭으로 -100%를 넘어가도 사용자 손실은 이 모형의 전용 담보 범위에서 종료하며, 초과분으로 다른 가용 잔고나 다른 계좌를 차감하지 않는다.

정상 종료 시 마지막 정산을 먼저 완료하고 `C + 실현 매매손익 - 종료 수수료`를 계산해 해당 계좌로 반환한다. 종료 비용 때문에 담보를 초과하는 경우도 모델상 반환액 0과 비용 한도 처리를 명시하고 잔액을 음수로 만들지 않는다. 펀딩·수수료·매매손익의 원장 합계와 반환액을 검증한다.

펀딩은 실제 지급 시각에 보유한 수량·기준가격·확정 요율로 계산한다. 고정 8시간 간격이나 최근 요율 하나로 전체 과거 구간을 계산하지 않는다. 정확한 펀딩 경계와 같은 시각의 주문·청산 순서는 규칙 버전으로 고정한다.

### 기본 테스트 벡터

비용·펀딩 0, P0=100, Q=10, M=100, 체결 레버리지 L=10일 때:

| 방향·가격 | 손익 U | 손익률 | 결과 |
|---|---:|---:|---|
| 롱, P=105 | +50 | +50% | 유지 |
| 롱, P=90.01 | -99.9 | -99.9% | 유지 |
| 롱, P=90 | -100 | -100% | 청산 |
| 롱, P=85 | -150 | -150% 관측 | 담보 범위에서 종료, 다른 잔고 차감 안 함 |
| 숏, P=110 | -100 | -100% | 청산 |

추가 벡터: 같은 롱에서 펀딩 -10이면 C=90, 청산가=91이다. 별도 경계 테스트로 P=100을 유지한 채 누적 펀딩 F=-100이면 E=0으로 청산된다. 후자는 펀딩만으로 조건에 도달하는 계산 검증용이며 실제 요율 예시가 아니다. 1배 롱의 비양수 임계 가격, 수량·잔고 경계, 소수점 정밀도도 다룬다.

가격 변동률, 레버리지 적용 ROE, 순손익, 계좌 수익률을 혼용하지 않는다. 청산은 표시용 반올림 문자열이 아니라 Decimal 계산값으로 판정한다. 신규 가격·수량·금액은 Decimal 또는 명시한 고정소수 표현을 사용하고 로컬 직렬화 및 API 변환 중 정밀도를 보존한다. 기존 Double 데이터는 유효성 검사 후 호환 변환하며 기존 데이터를 일괄 반올림해 덮어쓰지 않는다.

### 체결 레버리지는 변경 불가능한 거래 근거

주문에서 확정한 `leverageAtExecution`을 주문·포지션·거래 내역에 저장한다. 재실행 후에도 같은 값을 사용하며, 현재 주문 화면의 레버리지 선택값으로 기존 포지션을 재계산하지 않는다. PNL·공유 화면에도 실제 체결 레버리지를 전달한다. v1에서는 열린 포지션의 레버리지 변경을 허용하지 않는다.

```text
L = 주문 당시 검증한 레버리지
목표 명목금액 = M × L
목표 수량 = 목표 명목금액 / P0
실제 Q = 계약 수량 단위에 맞춰 내림한 수량
실제 명목금액 = 실제 Q × P0
매매손익 U = s × 실제 Q × (P - P0)
매매 ROE = U / M × 100
```

수량 내림 후 M은 고정 유지하는 안을 제안한다. 이 경우 실제 명목금액/M은 선택 L보다 조금 작을 수 있으므로 선택 레버리지와 실제 노출을 혼동하지 않는다. 증거금을 다시 산정해 차액을 반환하는 방식을 채택한다면 별도 규칙으로 확정하고 위 계산·저장·표시를 모두 일치시킨다. 실제 수량·명목금액·M을 저장해 재현하며, 내림 결과 Q=0이거나 최소 주문 조건 미달이면 체결하지 않는다.

Q에 이미 레버리지 효과가 들어 있으므로 U에 L을 다시 곱하지 않는다. 수수료와 펀딩은 해당 규칙의 실제 거래 명목금액과 기준가격으로 계산하며 증거금에만 요율을 곱하지 않는다. 비용 없는 P0=100, M=100에서 2배는 Q=2, 5배는 Q=5다. P=101이면 손익은 각각 +2/+5, ROE는 +2%/+5%이며 간이 롱 청산가는 50/80이다.

과거 선물 기록에 레버리지가 누락되면 임의로 1배를 넣지 않는다. 저장된 진입가·수량·증거금으로 검증 가능한 마이그레이션인지 판단하고, 선택 레버리지를 유일하게 복원할 수 없으면 원본 보존과 확인 필요 상태로 처리한다. 기존 현물에는 선물 레버리지를 억지로 채우지 않는다.

### 계산 실패가 자산 초기화로 이어지지 않는 계약

| 입력·실패 | 처리 |
|---|---|
| 가격·수량·증거금·레버리지 누락 또는 파싱 실패 | 계산 실패를 명시적으로 반환. `nil`/실패를 `0`으로 대체해 저장하지 않음 |
| P0≤0, Q≤0, M≤0 또는 지원 범위 밖 L | 주문/해당 정산 차단. 나눗셈 전에 분모 검증 |
| NaN·무한대·Decimal 연산 범위 초과·허용 정밀도 위반 | 입력과 각 연산 결과를 검사. 기존 스냅샷 유지, 실패 원인 기록 |
| 잔고 0, 손익 0, 펀딩 요율 0 | 정상 값으로 허용. 모든 필드에 일괄 양수 조건을 적용하지 않음 |
| 투자 원금 0인 수익률 | 나눗셈하지 않고 표시 불가로 처리. 잔고·이력은 유지 |
| 현재 시세 누락·상장폐지·조회 오류 | 마지막 확인값과 기준 시각 표시. 0원 평가/청산·보유 자산 삭제 금지 |
| 저장 데이터 손상·지원하지 않는 schemaVersion | 신규 이용자/빈 계좌와 구분, 원본을 보존하고 영향을 받는 변경 보류 |
| 인코딩·쓰기·교체 실패 | 자산·원장·체크포인트 모두 이전 확정 상태 유지. 저장 성공 안내 금지 |

가격 API의 문자열은 정밀도를 보존해 변환하고 통화별 저장 정밀도와 표시 반올림을 분리한다. 종료 반환액 하한처럼 명시된 거래 규칙 외에 잘못된 계산을 `max(0, …)`로 덮지 않는다. 기존 저장소의 특정 JSON `null`을 빈 배열로 해석하는 호환 경로는 기존 스키마에만 한정하고, 모든 디코딩 오류를 빈 데이터로 처리하는 규칙으로 확대하지 않는다.

## 7. 재접속 정산과 데이터 완결성

### 정산을 시작하는 사건

- 최초 앱 진입, foreground 복귀, 통신 재연결.
- 대상 선물 계좌 진입, 새 주문·전량 종료 전 필요한 검증.
- 광고 보상 등 잔고 사건 반영 전 필요한 시간 순서 검증.

여러 사건이 동시에 들어와도 계좌별 정산 실행은 합치고, revision으로 동시 변경을 감지한다. 한 계좌의 실패가 다른 거래소 현물이나 정산 완료 계좌를 막지 않는다.

### 앱 진입 시 보유 자산 업데이트 순서

1. 로컬 저장의 스키마·미완료 커밋을 확인하고 마지막 정상 스냅샷을 읽는다. 잔고·포지션·레버리지 오류를 신규 계좌 생성으로 덮지 않는다.
2. 기존 자산을 먼저 표시하되 마지막 확인 시각과 `정산 확인 중` 상태를 함께 표시한다. 마지막 표시값은 거래 가능한 최신 확정 잔고와 구분한다.
3. 현물 보유 코인은 해당 거래소의 현재 시세로 평가한다. 가격 하락만으로 현물 보유 수량을 청산하거나 삭제하지 않는다. 시세 실패 시 수량과 취득 원가는 보존한다.
4. 모든 열린 선물 포지션을 찾아 마지막 연속 검증 시각부터 이번 정산 기준 시각까지 과거 가격·펀딩을 확인한다. 현재 선택하지 않은 거래소도 포함한다.
5. 선물은 과거 최초 청산 사건을 먼저 확정한다. 현재 시세가 회복했거나 지금 광고로 충전했어도 과거 청산을 취소하지 않는다.
6. 검증된 잔고·포지션·원장·체크포인트를 같은 revision으로 저장한 뒤 최신 평가와 거래 가능 상태를 공개한다. 실제 확정 가능한 구간까지만 `confirmedThrough`를 전진시킨다.
7. 재생 중 받은 실시간 데이터는 계좌·상품·시각을 붙여 보관하고 과거 재생 이후 순서대로 연결한다. 더 새로운 현재가가 도착했다는 이유로 미검증 구간을 건너뛰지 않는다.

선물 상태는 `마지막 확인값 → 정산 중 → 거래 가능` 또는 `자료 부족/오류로 보류`로 구분한다. 거래 가능 여부는 계좌의 미검증 구간과 가격 신선도에 따라 판단한다. 오류 계좌만 신규 주문·종료 확정을 보류하며 독립된 현물·다른 계좌까지 일괄 막지 않는다. 전체 자산 요약은 미정산 항목을 포함한 값을 확정 총자산으로 표시하지 않는다.

앱 시작·Scene 활성화·foreground·재연결이 겹쳐도 같은 구간의 정산은 하나로 합친다. 화면마다 독립 정산기를 만들지 않는다. 장기 미접속 시 진행 상태와 재시도 경로를 표시하고, 시간 제한이나 제공자 보관 기간 초과를 청산 없음으로 해석하지 않는다.

```text
미완료 저장 복구
  → 열린 포지션·미정산 계좌 탐색
  → 현재 계좌 우선, 나머지는 제한된 동시 처리
  → 마지막 연속 검증 시각 이후 자료 조회
  → 가격·펀딩·주문·충전 사건 시간순 처리
  → 최초 청산 시 해당 포지션 종료
  → 잔고·원장·체크포인트 원자적 저장
```

- 진입 당시 체결가·시각을 저장한다. 차트를 뒤져 체결가를 다시 만들지 않는다.
- 현재가만 비교하면 중간 급락 후 회복을 놓친다. Mark Price 고저가를 포함한 구간 자료를 사용한다.
- v1은 우선 1분봉 순차 재생으로 정확성을 검증한다. 큰 봉으로 안전 구간을 건너뛰는 최적화는 실제 측정 후 추가한다.
- 거래소·상품·가격 종류가 같을 때만 가격 자료를 재사용한다. 같은 BTC라는 이유로 다른 거래소 자료를 쓰지 않는다.
- 펀딩·수량·비용·규칙 변경 경계에서 구간을 나눈다. 전체 기간에 현재 청산가 하나를 대입하지 않는다.
- 중복 봉, 역순 응답, 페이지 경계, 진행 중 봉, 누락 구간, 429·시간초과·거래 중단을 처리한다.
- 조회가 끝났다고 체크포인트를 올리지 않는다. 연속 구간 검증과 원장 저장이 완료된 곳까지만 전진한다.
- 모든 과거를 매번 다시 읽지 않는다. 원본 근거 보존 기간은 제공자 보관 기간과 충돌 복구 요구에 맞춰 정의한다.
- 실제 발생 시각을 알 수 없으면 발생 구간과 정산한 시각을 구분해 저장·표시한다.

### 부분 봉과 불명확한 순서는 출시 전 해결 조건

12:00:40 진입 후 12:00 봉 저가가 임계값을 넘었다고 해서 그 저가가 진입 후에 발생했다고 볼 수 없다. 종료 시각이 봉 중간인 경우도 같다. 일반 체결 틱으로 Mark Price 경로를 대체할 수 없다.

첫 가격 어댑터 조사에서 더 세밀한 동일 가격 자료의 제공 범위와 경계 구간 복원 가능성을 확인한다. 불가능하면 공개된 모의 판정 규칙 또는 별도 체결 모형을 제품 결정 사항으로 남긴다. 다음 분 체결은 이미 기본안에서 제외했으므로 에이전트가 임의로 되살리지 않는다.

자료가 없다고 포지션이 안전했다고 가정하거나, 임의로 손해가 큰 사건을 실제 청산 사실로 기록하지 않는다. 결정 전에는 `판정 확인 필요`로 처리하되 영구 보류를 해결책으로 삼지 않는다. 해당 정책 확정은 공개 출시 조건이며, 계좌 분리·광고 지급·순수 계산기 등 독립 작업까지 멈출 이유는 아니다.

## 8. iOS와 로컬 저장의 책임

### 기존 아키텍처에 맞춘 추가 위치

| 책임 | 제안 위치 |
|---|---|
| 거래 계좌·유형 식별 | `Mobit/Domain/Model/TradingAccount/` 또는 기존 모델 근처 |
| 선물 계약·포지션·원장 | `Mobit/Domain/Model/Futures/` |
| 순수 손익·청산 계산 | `Mobit/Domain/UseCase/Futures/` 내 독립 계산 타입 |
| 신규 주문·종료·재정산 | `Mobit/Domain/UseCase/Futures/` |
| 광고 보상 적용 | 두 실제 사용처가 공유하는 계좌 충전 UseCase |
| 선물 화면·Reactor·Coordinator | `Mobit/Presentation/FuturesScene/` |
| 선물 저장소 | `Mobit/Data/Repository/Futures/` |
| 거래소별 선물 REST·Socket·DTO | `Mobit/Data/Exchange/<Exchange>/` |

폴더와 타입은 실제 책임에 맞춰 최소로 만든다. 범용 TradingEngine 프레임워크나 사용되지 않는 Manager를 먼저 만들지 않는다. 현물 View의 기존 호출 구조 전체를 이번 작업에서 바꾸지 않는다.

View는 계좌·종목·방향을 포함한 사용자 입력을 Reactor에 전달한다. Reactor는 UseCase를 호출하고 UI 상태를 바꾼다. 순수 계산기는 Firebase·Supabase·UIKit을 알지 못하게 한다. 소켓 감시와 정산 작업 수명은 특정 주문 ViewController 수명과 분리한다.

### 저장 계약

- 사용자 계좌·주문·포지션·광고 보상·원장·정산 체크포인트는 로컬이 기준 저장소다. 로컬을 원격 계좌의 캐시로 취급하지 않는다.
- 로그인, Supabase Auth, 익명 원격 계정, 개인 원장 업로드, 기기 간 복원·동기화를 구현 범위에 넣지 않는다.
- Supabase가 필요하다면 공용 시세/설정 등 비개인 자료의 선택적 제공자로만 검토한다. 선물 MVP의 필수 의존성이나 사용자 잔고 저장소로 도입하지 않는다.
- 기존 UserDataManager의 잠금·스냅샷·복구 흐름을 검토한다. UserDefaults의 여러 키를 쓰는 동작이 디스크 수준의 단일 원자 커밋이라고 가정하지 않는다.
- 신규 선물은 Foundation 기반 파일의 검증된 스냅샷 교체 등 실제 실패를 감지할 수 있는 최소 로컬 저장 방식을 먼저 검토한다. 확정 잔고·포지션·원장·체크포인트·처리 ID는 동일 버전으로 저장한다. 현물 전체 저장 방식을 함께 교체하지 않는다.
- 로컬 저장이 실패하면 성공 UI·확정 상태·체크포인트를 공개하지 않는다. 실패 전 스냅샷을 보존하고 같은 requestID로 재시도한다. 앱 종료 후에는 검증된 커밋이나 복구 기록으로 재개한다.
- 저장소 안의 동일 자료를 하나는 UserDefaults, 하나는 파일에 각각 확정값으로 쓰지 않는다. 기준 스냅샷과 파생 캐시를 명시한다.
- 투자내역·더보기 충전은 같은 계좌 충전 UseCase를 사용하되 실제 저장은 현물/선물의 로컬 저장소에 위임한다.
- 앱 삭제·기기 변경 시 데이터가 유지되지 않는다는 제품 정책을 화면에 설명한다. iCloud/Keychain/원격 원장으로 숨은 복구 기능을 만들지 않는다. OS 백업·기기 이전·앱 오프로드는 완전 삭제와 다른 경로이므로 실제 저장 위치·백업 포함 여부를 검증한다. 정책과 충돌하면 범위를 보고하고 필요한 최소 저장 설정을 별도로 검토한다.
- 상시 가격 수집, Cron, 매분 Edge Functions 실행, 별도 서버 설치를 추가하지 않는다.

로컬 모델에서는 원격 서비스 장애 때문에 기존 자산 조회가 불가능해져서는 안 된다. 다만 최신 시세·누락 구간이 없으면 마지막 확인 자산을 표시하고 필요한 거래·정산만 보류한다. 개인 원장이 로컬에만 있으므로 기기 수준 데이터 조작 방지나 기기 간 보상을 동일 사용자로 통합하는 기능을 보장하지 않는다.

### 동시 변경과 복구의 필수 불변 조건

현재 `NSRecursiveLock`과 `performAtomicInvestmentUpdate`는 활용할 기반이다. 그러나 getter와 setter가 각각 잠겨 있어도 `읽기 → 수정 → 쓰기` 전체가 원자적인 것은 아니다. 특히 광고 콜백의 잔고 `+=`, 초기 지급, 주문, 정산, 초기화가 같은 자산에 접근하는 경로를 함께 조사한다.

| 경계 | 구현 기준 |
|---|---|
| 상태 변경 소유권 | 자산을 변경하는 단일 직렬화 경로를 두고 모든 쓰기가 통과. 기존 잠금/직렬 큐를 우선 검토하며 actor 도입 자체를 해결책으로 간주하지 않음 |
| 거래 단위 | 스냅샷 읽기·검증·계산·원장 추가·저장·revision 갱신 전체를 하나의 변경 단위로 취급 |
| 여러 계좌의 공유 저장 | 계좌별 잠금만으로 공유 딕셔너리 덮어쓰기를 허용하지 않음. 실제 저장 단위에 맞춰 직렬화 |
| 네트워크 대기 | 잠금 밖에서 수행. 요청 시 AccountID·InstrumentID·revision·데이터 세대 고정, 반영 직전 다시 검증 |
| 충돌 | 기다리는 동안 잔고/포지션이 변했으면 최신 상태로 재검증·재계산. 오래된 계산 결과를 덮어쓰지 않음. actor 사용 시 await 재진입도 같은 기준 적용 |
| 중복 | 주문 requestID, 광고 rewardClaimID, 포지션별 펀딩 사건 키, 청산 사건 키를 원장과 같은 커밋에 저장 |
| 초기화·화면 전환 | 초기화는 데이터 세대를 바꿔 이전 응답이 삭제된 자산을 되살리지 못하게 함. 화면 전환은 주문 대상을 바꾸지 않음 |
| UI 공개 | 저장에 성공한 불변 스냅샷만 메인 스레드에서 전달. UI 캐시나 Reactor State를 별도 자산 원본으로 사용하지 않음 |
| 저장 복구 | 인코딩·검증 후 원자적 교체를 검토하고 실패 시 마지막 정상 데이터 보존. pending 기록의 스키마·revision·중복 키를 검증한 뒤 한 번만 복구 |

앱 내 초기화와 이미 획득한 광고 보상이 겹치는 정책도 명시해야 한다. 구현 제안은 미완료 보상 커밋 중 초기화 실행을 보류하고 안내하는 방식이다. 뒤늦은 콜백을 무조건 재지급하거나 이미 획득한 권리를 조용히 삭제하지 않는다. 단, 보상 SDK의 콜백 수신과 최초 로컬 기록 사이에 프로세스가 종료되면 로컬 전용 구조만으로 획득 사실을 완전히 복원할 수는 없다. 저장된 사건의 중복 방지·복구 범위와 이 한계를 구분한다.

동시성 검증은 Thread Sanitizer와 순서를 통제하는 테스트를 함께 사용한다. Sanitizer 통과만으로 오래된 스냅샷 덮어쓰기·이중 보상 같은 논리 오류가 없다고 판단하지 않는다. 실패 주입 위치는 인코딩 전후, 파일 교체 전후, 메모리 상태 공개 전후, 네트워크 응답과 다른 거래의 사이를 포함한다.

W4/W5는 입력·출력 계약이 정해지면 독립적으로 진행할 수 있다. 가짜 로컬 저장소와 고정 가격 자료로 계산·정산을 검증할 수 있다. 이 문서는 별도 에이전트 생성이나 병렬 실행을 요청하지 않으며, 위 순서는 단일 에이전트도 수행할 수 있다.

P0는 자금 정합성·데이터 보존·재진입 정산의 필수 작업이다. P1은 첫 선물 기능 출시 연결 작업, P2는 후속 기능이다. USDT 보상 1,000은 확정되어 있으므로 재질문하지 않는다. 아직 지원하지 않는 시장의 정책 정의와 실제 거래 활성화는 별도 단계다.

### 작업별 보고 형식

각 W 작업을 마칠 때 `완료 범위 / 변경 파일 / 검증 결과 / 미결정·미수행 항목 / 다음 작업`을 기록한다. 계획상 완료 조건을 만족하기 전에는 완료 표시하지 않는다. 구현 중 범위가 달라지면 사용자 확정 정책과 에이전트 제안을 구분해 문서를 갱신한다.

## 10. 검증표

### 자금과 계좌

- [ ] 최초 선택 거래소가 Upbit가 아니어도 최초 100만원은 업비트 현물에만 귀속된다.
- [ ] 다른 현물/선물 계좌는 생성·전환·재시도 시 0으로 시작하며 자동 지급이 없다.
- [ ] 기존 Bithumb 잔고·보유 코인·거래 내역·광고 충전분이 보존된다.
- [ ] 초기화·앱 업데이트·마이그레이션이 최초 지급 자격을 복구하지 않는다.

- [ ] A 현물/A 선물/B 선물의 같은 심볼이 별도 식별된다.

### 광고 충전

- [ ] reward callback 없이 dismiss만 발생하면 미지급.
- [ ] reward 후 dismiss, dismiss 후 reward, reward 중복에서도 최대 한 번 지급.
- [ ] 광고 로드/노출 실패 시 잔고 불변, 로딩 상태 해제.
- [ ] A에서 광고 시작 후 B 선택 시 A에 지급.
- [ ] 광고 시청 중 ViewController 해제·foreground 복귀·통신 실패 후 권리 복구.
- [ ] 보상 저장 성공 뒤에만 완료 표시, 재시도에 광고 재시청 불필요.
- [ ] KRW 보상 수치가 USDT 계좌에 그대로 들어가지 않음.
- [ ] 보상 사건과 잔고가 함께 저장되고 PNL은 증가하지 않음.
- [ ] 지원 USDT 계좌의 보상은 정확히 1,000 USDT, 현재 KRW 보상은 기존 정책 유지.

- [ ] 로그인/원격 개인 원장 없이 작동하고, 신규 설치와 손상 데이터가 구분됨.

- [ ] 주문·광고·정산의 읽기-수정-쓰기 교차 실행에서도 원장 합계와 잔고가 일치.
- [ ] 공유 딕셔너리의 다른 계좌 동시 변경이 서로를 덮어쓰지 않음.
- [ ] 초기화 후 늦은 응답이 이전 자산을 복원하지 않으며 미완료 광고 보상 정책 준수.

- [ ] 롱·숏 손익 부호, 레버리지·수량, -99.9/-100/-100 초과 경계.

- [ ] 기존 현물 주문·잔고·BTC 결제·소켓 테스트 통과.

### 빌드와 보고

실제 코드 구현 시 `xcrun simctl list devices available`로 사용 가능한 시뮬레이터를 확인하고 `Mobit-Dev` 스킴으로 빌드·관련 테스트를 수행한다. 광고 SDK·리소스·SPM·Xcode 설정 변경이 있으면 Mobit/Release 영향도 확인한다. 새 파일은 target membership을 확인한다.

문서 작성 단계에는 빌드·런타임 검증을 수행하지 않았다. 코드 구현 단계의 검증 결과는 아래 진행 기록에 남긴다. 각 단계의 완료 보고에는 변경 파일, 검증 명령·결과, 미수행 항목, 남은 출시 조건을 명시한다.

### 세 번째 변경 단위: W4 레버리지 고정 포지션·원장·순수 계산

완료 범위:

3. 평가손익·ROE·예상 청산가·부호 있는 펀딩·종료/청산 견적을 순수 함수로 제공한다. 청산 여부는 표시용 ROE 반올림값 대신 자본 `M + F - 진입수수료 + U <= 0`으로 판단한다.
4. 종료 수수료는 남은 포지션 자본까지만 차감하고, 급변으로 발생한 증거금 초과 손실은 `absorbedLoss`에 구분한다. 다른 가용 잔액을 차감하지 않는다. v1 청산 견적에는 별도 청산 수수료를 적용하지 않는다. 실제 거래소 cross/isolated 규칙이 아닌 간이 계산 계약이다.
5. 모든 금액 계산은 Decimal 입력 검증과 연산 오류 검사를 거친다. 0 나누기, NaN, 음수/0 가격·증거금, 범위 밖 레버리지, 잘못된 계약/시각, 최소 수량·금액 미달, overflow/underflow를 거절한다. 순환소수 나눗셈만 명시적으로 정밀도 손실을 허용하고 주문 금액 상한을 재검증한다. Foundation이 `1e-128 × 1e-128`을 오류 없이 1로 반환하는 경계 사례를 확인하여 곱셈/나눗셈의 지수 합/차가 -128...127을 벗어나면 보수적으로 거절한다. 가수 재조정으로 표현 가능할 수 있는 극단값도 이 범위 검증에서는 허용하지 않는다.
6. 선물 파일 schema 3에 포지션과 진입 원장을 추가했다. 기존 schema 1/2의 잔고·보상 기록을 유지하며 다음 커밋부터 새 형식으로 저장한다. schema 3 필수 필드 누락/null, 중복/고아 원장, 변조된 수량·수수료는 오류로 처리하고 파일을 보존한다.
7. 진입은 잔액 차감·포지션·원장·revision을 잠금 안에서 한 번에 원자 교체한다. 같은 requestID의 동일 주문은 재차감하지 않고, 다른 내용이면 거절한다. 오래된 revision, 부족한 잔고, 같은 계좌/종목의 추가 진입은 거절한다. 광고 충전은 포지션과 원장을 보존한다.

### 다섯 번째 변경 단위: W6 1차 — 닫힌 구간 정산과 앱 진입 연결 (2026-09-28)

3. 첫 조회 시작은 실제 진입 시각이며 이후에는 저장된 `verifiedThrough`를 사용한다. 진입 시각이 ms보다 정밀하면 올림해 진입 이전 시간을 포함한 판정을 피한다. 캔들은 해당 시각이 속한 분 시작부터 조회하되, 실제 판정 시작과 캔들 범위를 구분한다.

5. 순수 재생기는 롱의 저가/숏의 고가로 중간 청산을 확인한다. 완성 봉에서 청산 후 가격이 회복해도 청산을 취소하지 않는다. 정확한 발생 시각을 꾸미지 않고 발생 구간·근거 Mark·정산 시각을 구분해 기록한다. v1 손실 한도는 진입 증거금이며 가용 잔액을 다시 차감하지 않는다.
6. 진입 부분 봉도 전체 고저가가 안전하면 해당 부분 구간의 안전성은 입증 가능하므로 전진한다. 부분 봉이 임계값을 넘으면 진입 전/후를 구분할 수 없어 `ambiguousEntryCandle`로 보류한다. 다음 분 체결이나 임의의 불리한 체결로 바꾸지 않는다.
7. 펀딩이 있는 봉에서는 펀딩 전과 각 사건 반영 후의 담보에 대해 전체 봉의 불리한 가격에서도 안전한지를 검사한다. 모두 안전할 때만 해당 봉의 실제 펀딩을 순서대로 반영한다. 청산 가능성이 있거나 진입 시각과 펀딩이 같으면 `ambiguousFundingOrder`로 보류한다. 펀딩 Mark가 같은 봉 범위를 벗어나도 자료 모순으로 보류한다.
8. 보류 봉 앞의 연속 검증 구간은 저장한다. 해당 봉 안의 일부 펀딩만 반영하지 않는다. 최초 확인 청산 이후 사건은 적용하지 않는다. 분할 재생과 한 번의 재생이 같은 상태를 만드는 것을 검증한다.
9. 선물 schema 4에 포지션별 체크포인트·누적 펀딩·개별 펀딩 원장·마지막 검증 Mark·청산 기록을 추가한다. schema 1~3은 기존 진입 정보로 초기 상태를 유도하고 다음 쓰기에서 이관한다. schema 4 필수 정산 배열 누락/null, 고아/중복 상태·잘못된 수치/누적액은 저장을 거절한다.
10. 정산 상태와 계좌·기존 진입 원장·광고 지급 기록을 같은 파일 커밋으로 교체한다. 원래 `ledger`는 진입 원장을 유지하고, 펀딩 사건 원장은 `reconciliations.fundingReceipts`, 청산 사건은 `reconciliations.liquidation`에 저장한다. 성공 전 체크포인트를 공개하지 않는다. 오래된 revision이면 정산 결과를 버리고 재시도 필요 상태로 반환한다.
11. 포지션은 청산 후에도 감사·주문 ID 중복 방지를 위해 보존한다. 활성 여부는 정산 상태의 liquidation으로 구분한다. 같은 종목 재진입은 가능하지만 이전 주문 ID를 재시도해도 새 포지션을 만들지 않는다. 같은 계좌의 다른 활성 포지션이 주문 시각까지 검증되지 않았다면 신규 주문을 거절한다. 광고 충전은 계속 허용한다.
12. 요청별 20초 timeout과 포지션당 한 실행 8페이지 상한을 둔다. 초과 시 저장된 체크포인트와 `workLimit`을 반환한다. 다음 활성화/명시적 refresh에서 이어간다. 하나의 포지션 오류가 다른 포지션 처리를 막지 않는다. 미지원 제공자는 명시적으로 보류하고 현물로 대체하지 않는다.

- KRW/BTC 마켓을 대상으로 시장 가격과 계좌 담보 통화를 구분한다. USDT 1,000 광고 보상은 미래 정책으로 유지한다. 계산기·저장소·주문 검증은 국내 KRW/BTC 계좌를 처리하도록 수정했다. 국내 시세 API 및 UI 연결은 아직 완료하지 않았다.

timestamp 기반 과거 검증:

1. 실제 진입 시각(ms), 대상 거래소/원본 마켓, 체결가·수량·레버리지를 보존한다.
2. 진입 경계 구간은 해당 거래소의 초봉 또는 공개 체결 이력을 조회해 진입 이후만 비교한다. 분봉에서 초봉을 생성하는 것이 아니라 별도 정밀 자료를 조회하는 것이다.
3. 업비트는 `/v1/candles/seconds`를 제공한다. 공식 문서 기준 최근 3개월, 요청당 최대 200개이며 무체결 초에는 봉이 없다. 따라서 기존 Binance의 연속 1분봉 개수 검사를 국내 초봉에 그대로 적용하면 안 된다.
4. 12:31:34.500 진입처럼 초 중간에 진입하면 34초 봉에도 진입 전 거래가 섞일 수 있다. 가능한 범위에서 ms timestamp가 있는 체결 이력으로 추가 판정한다. 동일 timestamp의 사건 순서·조회 기간 제한은 별도 검증한다.
5. 빗썸은 공식 공개 체결 이력 API와 cursor를 경계 구간 복원에 사용한다. 공식 문서 기준 daysAgo 1~7일, 최대 500건이며 to는 KST다. 업비트 체결 조회는 days_ago와 UTC 기준이므로 같은 파라미터/시간대 처리를 공유하지 않는다. 공식 문서 목록에서 초봉 API는 확인하지 못했으므로 업비트와 동일한 초봉 기능을 가정하지 않는다.
6. 전체 분이 보유 기간에 포함되면 분봉 고저가로 검사하고, 임계값 도달 시 세부 자료로 최초 발생 범위를 좁힌다. API 조회 한도·역순/중복·기간 제한·무체결과 실패를 구분한다.
7. 사용자가 선택했던 첫 분 마감가 모의 규칙은 정밀 조회가 불가능하다는 잘못된 전제에서 제안됐다. 정밀 자료로 해결할 수 있는 구간에 이를 강제하지 않는다. 복원 불가능한 경계에 적용할 fallback의 정확한 범위는 재정리한다.

- 국내 KRW 포지션의 앱 재진입 정산에 해당 제공자를 연결했다. 해외 제공자로 대체하지 않고 펀딩 요청도 하지 않는다. 선물 계약 조회 API가 없는 국내 거래소에 임의의 계약 규칙을 생성하지 않으며 `contract` 호출은 오류를 반환한다.
- 업비트 분봉 요청은 UTC, 빗썸은 KST로 구성한다. 응답 봉 시각은 UTC로 해석하고 서버 HTTP Date로 완료된 봉인지 확인한다.
- 499분 검증 구간을 최대 199분씩 나누어 200개 봉을 요청한다. 시작 이전 기준 봉까지 확보한 응답에서만 빠진 구간을 직전 종가로 채운다. 빈 응답, 기준 봉 누락, 중복 봉, 잘못된 OHLC, 서버 시각 누락, API 오류는 검증 실패로 남긴다.
- 초봉의 보존 범위 밖 요청은 빈 정상 응답으로 바꾸지 않는다. 체결 조회는 cursor를 반환하는 한 페이지 조회이며, 이것만으로 기간 전체를 검증했다고 간주하지 않는다.
- 날짜 파서는 응답마다 생성해 그 응답의 봉에서 재사용한다. 요청 간 가변 파서를 공유하지 않는다.
- 신규 앱 파일 2개와 테스트 파일 1개만 Xcode의 해당 타깃에 등록했다. 의존성과 빌드 설정은 변경하지 않았다.

검증 범위:

- 실제 업비트·빗썸 공개 분봉 API가 모두 HTTP 200을 반환하는 것과 같은 시간 구간, 응답 필드를 확인했다. 실제 초봉·체결 페이지의 장기간 복원은 아직 검증하지 않았다.
- 추가 단위 테스트는 시간대/파라미터, Decimal, 잘못된 응답, 무체결 구간, 499분 분할, 초봉 제한, 체결 cursor, API 응답에서 청산 저장·거래 내역·실현 PNL까지의 통합 경로를 다룬다.

다음 구현 순서:

1. 진입 직후와 현재 진행 구간을 초봉/체결 페이지로 복원한다. UTC/KST 날짜 경계, 페이지 연속성, 보존 기간 소진을 구분하고, 세부 자료가 복원 불가능한 진입 경계에만 합의한 마감가 규칙을 적용한다.
2. 실제로 검증한 끝점과 주문 실행 시점의 관계를 정의해 preflight에 연결한다. 현재 완료 분봉만으로는 기존 활성 포지션의 주문 직전 검증을 충족하지 못하므로 임의로 timestamp를 앞당기지 않는다.
3. 동일 조건 추가 진입과 수동 종료 원자 저장, 평가 시세 신선도/손익 표시 일관성을 보완한 뒤 KRW 전용 UI를 연결한다.

현재 UI에서 선물 주문을 테스트할 수 있는 단계는 아니다. 초봉/체결 조회 코드의 존재를 경계 정산 완료로 해석하지 않는다.

최종 검증: `Mobit-Dev` / iPhone 16 (iOS 26.3) Simulator, Thread Sanitizer 활성화 전체 단위 테스트 216개 통과(실패 0). 해당 실행에 Thread Sanitizer 경고 없음. 최초 실행의 499분 테스트는 5초 제한으로 실패했고, 응답 단위 날짜 파서 재사용 및 테스트 대기 시간 조정 후 전체 재실행에 통과했다. 로그: `/tmp/mobit-domestic-market-tests.log`. `git diff --check` 통과. 기존 중복 rpath/AppIntents 경고는 유지된다. 커밋과 스테이징은 수행하지 않았다.

## 2026-09-29 UI 연결 전 구현 상태

이 절이 앞의 미완료 목록과 과거 설계보다 우선한다. 화면은 활성화하지 않았고 UI가 호출할 국내 선물 주문·정산·조회 경로를 구현했다. 선물 계좌의 UI 지원 표시는 아직 `preparing`이다.

### 1. 시간 검증과 재접속

- 완료된 분은 분봉으로, 진입/추가 진입 분과 현재 진행 구간은 체결 이력 또는 업비트 초봉으로 검사한다. 검사 끝은 시세 timestamp **포함**이며 마지막 밀리초의 급락도 누락하지 않는다.
- 초봉은 정수 초 경계에서 사용하고, 초 내부의 밀리초 구간은 체결 이력을 사용한다. 체결 페이지는 시간 순서·cursor 진행·중복·서버 날짜·상한 시각을 확인한다. 일자 계산은 업비트 UTC, 빗썸 KST를 사용한다.
- 업비트 체결 보존 7일/초봉 3개월을 기준으로 세부 복원이 불가능한 진입 분에만 마감가 규칙을 적용한다. 추가 진입은 새로운 증거금·평균가 조건이 시작되는 경계이므로 같은 규칙을 적용한다. 적용 구간은 `entryCloseFallbacks`에 남긴다. HTTP 오류·파싱 실패·누락·페이지 작업 한도는 마감가로 대체하지 않는다.
- 빗썸 공개 API에서 동일 밀리초 체결들이 같은 `sequential_id`를 쓰는 응답을 실제 확인했다. 같은 페이지의 가격들은 모두 검사하고 최대 5초 구간으로 나누어 요청한다. 500개 응답이 검사 시작점에 도달하지 못하면 cursor로 잘린 체결을 건너뛰지 않고 보류한다. 이 경우 사용자는 정산이 끝난 것으로 안내받아서는 안 된다.
- 현재 진행 중인 분의 **안전 판정**은 해당 revision의 주문 준비 증명으로만 사용한다. 장기 저장 체크포인트는 완료 분 경계를 유지해 몇 달 뒤 체결 보존 기간이 지나도 분봉으로 재개할 수 있게 한다. 실제 청산은 진행 중인 분에서도 즉시 저장한다. 진입·추가 진입·종료 시각과 청산 발생 구간은 별도로 보존한다.
- 앱 활성화 시 정산하고 포그라운드에서는 완료 후 3초 뒤 재검사한다. 과거 작업 한도는 1초 뒤 이어서, 요청/자료 오류는 15초 뒤 재시도한다. 백그라운드 전환 시 취소하고 새 주문 준비도 차단한다. 서버·서버 스케줄러·푸시는 추가하지 않았다.

### 2. 주문·추가 진입·수동 종료

- 계좌 진입/재조회는 `FuturesTradingUseCase.accountSnapshot(for:)`로 연결해 신규 KRW 선물 계좌만 0원으로 생성하고 기존 잔액을 보존한다. 주문 진입점은 `open`/`close`다. `requestID`를 사용자 주문 단위로 유지해야 한다. 추가 진입은 `addingTo`에 기존 포지션 ID를 전달하여 검증 도중 청산된 포지션을 신규 주문으로 다시 열지 않게 한다.
- 시장가로 준비한 시세의 가격을 사용하되, 체결 시각은 시세를 받은 시점에 고정한다. 거래소의 과거 시세 timestamp로 사용자 진입 시각을 소급하지 않는다. 저장 직전 5초 이내 시세인지, 계좌 revision이 같은지, 기존 포지션이 그 시점까지 검증됐는지 재검사한다. 미검증 구간을 단순 현재가로 메우지 않는다. 준비 시간이 길거나 잔액이 바뀌면 명시적인 재준비가 필요하다.
- 국내 주문은 수수료 0, 종목별 레버리지 상한, 수량 0.00000001 단위 내림, 기존 KRW 최소 주문금액 500원의 명목금액 기준을 사용한다. 현물 주문 계산과 체결 정책은 수정하지 않았다. 국내 `contract` API로 실제 선물 규칙을 만들어내지 않는다.
- 같은 거래소·마켓에서 방향과 레버리지가 같은 경우에만 추가 진입한다. 최초 주문과 개별 추가 체결을 보존하고 총수량·총증거금·명목금액·평균 진입가·청산가·ROE를 갱신한다. PNL은 반올림한 평균가를 다시 곱하지 않고 총명목금액으로 계산한다.
- 수동 종료는 전량 종료다. 증거금과 확정 PNL을 가용 잔고에 반환하고 종료 기록과 원장을 같은 파일 교체에 포함한다. 기존 포지션은 내역 자료로 보존하고 활성 목록에서는 제외한다. 청산된 포지션은 수동 종료할 수 없다.
- 추가 진입/종료도 광고 보상과 동일 저장소 잠금·revision·원자 파일 저장을 사용한다. 같은 요청 ID 재시도는 이미 저장한 결과를 반환한다. 저장 실패는 이전 바이트와 잔액을 보존한다.

### 3. 내역·PNL·평가 조회

- `snapshot.isActive`로 활성 포지션을 구분한다. `position.order`는 최초 체결이며 최신 평균가는 `averageEntryPrice`, 총증거금은 `margin`, 최종 체결 시각은 `lastExecutionAt`, 개별 체결은 `executions`를 사용한다.
- `transactionHistory(for:)`에서 최초 진입·추가 진입·수동 종료·청산을 조회한다. 실현 PNL은 종료 사건만 합산하고 광고 충전은 수익으로 계산하지 않는다.
- `valuation(for:quotes:now:)`는 가격·종목·시각을 검사하며 누락/미래/30초 초과 시세로 확정된 평가를 만들지 않는다. 미검증 상태는 `requiresReconciliation`과 저장된 검증 시각으로 전달한다. 현재 분의 실시간 검사 결과는 정산 서비스 상태도 함께 확인한다.
- 포지션 표시에는 `FuturesValuation.displayedPnL`, `displayedROEPercent`, `displayedEquity`를 사용한다. 청산 판정용 원시 가격 손실은 보존하지만 화면 손실은 증거금 전액, ROE는 -100%, 평가자산은 0을 하한으로 한다. 계좌 총자산과 표시 손익이 모순되지 않는다.
- 저장 스키마 5는 추가 체결과 수동 종료를 포함한다. 기존 1~4 스키마의 잔고·포지션·광고 보상은 읽기 호환을 유지하며 다음 정상 저장 때 갱신한다. 현물 초기화 범위에 선물 삭제를 임의로 추가하지 않았다.

### 4. UI 연결 시 수행할 작업

1. 거래소별 현물/선물 선택과 국내 선물 KRW 전용 마켓을 제공한다. 선물 BTC 탭은 숨긴다.

## 2026-10-01 W8 선물 UI 연결

이 절이 위의 UI 미연결/준비 중 설명보다 우선한다. 업비트·빗썸 KRW 선물 계좌를 UI에서 활성화했다. 해외 거래소·BTC 선물·Cross/Isolated 선택은 추가하지 않았다.

### 화면 흐름

1. 거래소·투자내역 화면에서 하단 탭바 위 캡슐형 `현물 / 선물` 버튼으로 전환한다. 현재 모드를 로컬에 기억하고 거래소 변경에도 유지한다. 상세·뉴스·더보기에서는 전환 버튼을 숨긴다.
2. 선물 화면은 거래소별 KRW 계좌의 총 평가자산·주문가능·평가손익·실현손익, 원화 종목 검색/즐겨찾기 필터/정렬, 포지션, 거래내역, PNL을 제공한다. 신규 계좌는 0원이며 보상광고 완료 시 해당 선물 계좌에 1,000만 원을 지급한다.
3. 종목 상세의 기존 차트·정보를 재사용하고 주문 영역만 선물 전용으로 연결한다. 롱/숏·종목별 레버리지·원화 증거금 입력, 명목금액 안내, 같은 조건 추가 진입, 확인 후 전량 종료를 제공한다.
4. 포지션 카드에 평균 진입가·수량·총증거금·진입 레버리지·손익/ROE·청산 기준가·최초 진입·저장된 검증 경계를 표시한다. 추가 진입 시 방향/레버리지를 잠그고 기존 포지션 ID를 전달한다. 검증 중 청산된 상세에서 재진입되지 않도록 주문을 차단한다.
5. 청산·수동 종료 내역과 실현 PNL은 같은 저장 스냅샷에서 조회한다. 청산 발생 구간과 실제 정산 시각을 구분한다. 조회 실패는 자산 0원으로 대체하지 않고 대기/오류로 표시한다.
6. 더보기 충전도 선택된 현물/선물 계좌로 연결한다. 초기화는 기존 현물 범위를 유지하고 화면 문구에 명시했다.

### 연결 및 정합성

- `FuturesCoordinator`가 선물 거래소/투자내역의 Reactor와 시세 Reactor를 공유하고 Coordinator 경로로 상세 화면을 연다. 현물 주문 뷰는 선물 상세에서 생성하지 않는다.
