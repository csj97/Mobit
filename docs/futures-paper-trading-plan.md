> **최신 정책: 국내 선물은 KRW 전용·수수료/펀딩 없음·증거금 소진 청산. 문서 마지막 확정 정책을 우선한다.**

> **2026-09-29 범위 정정 — 아래 과거 설계/구현 기록보다 이 정정을 우선한다.**
> 이번 기능은 **업비트·빗썸의 현물 시세를 이용한 MOBIT 내부 선물 모의거래**다. 실제 주문 전송은 없으며 Binance·OKX·Bybit 지원은 추후 범위다. 기존 USDT 무기한/해외 Mark Price/해외 펀딩 중심 설계와 W5·W6 완료 평가는 국내 목표에 대한 완료로 간주하지 않는다. 상세 변경 기준은 문서 마지막의 범위 정정을 따른다.


작성일: 2026-09-21. 최종 검토일: 2026-09-22. 최신 사용자 요청을 반영한 제안 문서다. 실제 자금 거래가 아닌 모의투자를 전제로 한다. 기존 문서의 매분 서버 정산, Cron, 다음 분 경계 체결 제안은 현재 기본안에서 제외한다. 구현 순서와 상세 기준은 [에이전트 작업 계획](futures-agent-implementation-plan.md)을 우선 참고한다.

## 1. 확정된 방향과 제안의 구분

사용자가 명시한 방향:

- MOBIT은 N개 거래소를 지원하는 구조다.
- 각 거래소 아래에 현물과 선물을 구분할 수 있어야 한다.
- 선물은 앱 재진입 시 미접속 구간을 확인하는 방식으로 구성한다.
- 로그인 없이 사용하며 개인 자산·거래 내역은 모두 로컬에 저장한다. 앱 삭제·기기 변경 시 기존 데이터를 복구하거나 동기화하지 않는다.
- 현재 국내 거래소 KRW/BTC 마켓만 지원한다. 향후 USDT 지원 계좌의 광고 보상은 1회 1,000 USDT로 정한다.
- 최초 업비트 현물 계좌에만 1,000,000 KRW를 지급하고 나머지 신규 계좌는 모두 0으로 시작한다.
- 부족한 자금은 해당 계좌에서 광고 시청 보상으로 충전한다. 계좌 간 이체 개념은 도입하지 않는다.
- 최종 목표는 cross/isolated 선택 지원이다. 첫 버전은 구분 없이 포지션 손익률 -100%에서 청산하는 간이 정책으로 시작할 수 있다.
- 동시 변경이나 잘못된 계산으로 기존 자산을 잃지 않아야 한다. 체결 레버리지 보존과 앱 진입 시 보유 자산 확인을 필수 조건으로 둔다.

아래 사항은 구현을 위한 제안이며 아직 확정 요구사항은 아니다.

- 거래소별 현물·선물 계좌를 독립시킨다. 이체 UI/API/원장은 만들지 않는다.
- 선물 첫 버전은 USDT 선형 무기한, 롱/숏, 전량 종료와 간이 -100% 청산으로 제한한다. 실제 cross/isolated 구현 전에는 해당 선택지를 활성화하지 않는다.
- USDT 선물 계좌가 지원되면 0 USDT로 시작하고 광고 획득 시 1,000 USDT를 충전한다. 현재 미지원 마켓을 정책 정의만으로 활성화하지 않는다.
- 앱에서 계산하고 로컬에 저장한다. Supabase는 필요할 때 공용 시세·설정 제공 용도로만 검토하며 개인 원장 저장·로그인·상시 수집 서버·예약 함수·Cron을 필수로 두지 않는다.
- 다중 거래소를 담을 구조를 먼저 만들되, 실제 활성화는 거래소별 데이터 검증 완료 후 진행한다.

## 2. 화면과 계좌의 기본 구조

```text
MOBIT
├─ 거래소 A
│  ├─ 현물: 잔고 / 보유 코인 / 주문 / 거래 내역 / PNL
│  └─ 선물: 잔고 / 증거금 / 포지션 / 주문 / 거래·펀딩·청산 내역 / PNL
├─ 거래소 B
│  ├─ 현물: 독립 계좌
│  └─ 선물: 독립 계좌
└─ 거래소 N
   ├─ 현물: 지원 상태에 따라 활성
   └─ 선물: 지원 상태에 따라 활성
```

권고 선택 순서는 `거래소 → 현물/선물 → 결제 마켓·계약 → 종목`이다. 거래소 A/B는 설명용 이름이며 특정 거래소의 실제 지원 범위를 주장하지 않는다.

화면 상단에 현재 거래소와 거래 유형을 함께 표시한다. 현물의 KRW/BTC 등 마켓 선택과 선물의 USDT 무기한 등 계약 선택을 같은 의미의 탭으로 취급하지 않는다. 전환 후 종목 목록·잔고·주문 양식·차트·거래 내역·PNL이 모두 같은 선택 범위를 따라야 한다.

모든 거래소가 실제로 선물 데이터와 계약을 제공한다고 가정하지 않는다. 지원되지 않는 조합은 `미지원`, 준비 중인 조합은 `준비 중`, 정상 운영 중 장애는 `일시 이용 불가`로 구분한다. 다른 거래소의 데이터를 조용히 대신 사용하지 않는다. 특정 거래소 이름 아래에 가상 선물 상품을 제공하려면 실제 거래소 선물과 구분하는 별도 상품 기획이 필요하다.

거래소별 마지막으로 사용한 거래 유형을 기억하되, 더 이상 지원하지 않으면 지원 가능한 화면으로 돌아가 이유를 표시한다.

## 3. 시나리오 1: 기존 사용자가 현물을 이용한다

1. 기존에 선택했던 거래소의 현물 화면으로 진입한다.
2. 기존 현물 잔고·보유 자산·거래 내역·PNL을 그대로 표시한다.
3. 거래소 A의 현물 매수는 A 현물 계좌만 변경한다.
4. A 선물, B 현물, B 선물 잔고에는 영향을 주지 않는다.

기존 데이터에는 거래 유형을 현물로 해석하는 호환 처리를 둔다. 기존 키와 기록을 일괄 변경하거나 초기화하지 않는다. 현물과 선물 데이터가 실제로 합쳐지는 경계에서 새 식별자를 사용한다.

## 4. 시나리오 2: 같은 거래소에서 선물로 전환한다

예: `거래소 A > 현물`에서 `거래소 A > 선물` 선택.

1. A 선물 지원 여부를 확인한다.
2. 지원하면 A 선물 계좌를 읽는다. 처음 이용하는 경우 0 잔고로 생성하고 광고 충전을 안내한다.
3. A 현물 잔고를 복사하거나 자동 환전하지 않는다.
4. A의 선물 지원 종목, 선물 차트, 주문 양식을 표시한다.
5. 기존 A 선물 포지션이 있으면 미정산 구간 확인 상태를 표시한다.ㅇ

최초 업비트 현물 100만원 지급은 중복되지 않게 기록하고 그 외 계좌 생성은 무상 자금을 발생시키지 않는다. 광고 보상은 시작 시 대상 계좌를 고정하고 실제 보상 획득 사건당 한 번만 지급한다. 탭 전환·앱 재실행·요청 재시도로 자금이 중복 지급되지 않아야 한다. 중복 방지의 범위는 현재 로컬 데이터이며, 앱 삭제·기기 변경 시 계정 인증을 통한 복구는 제공하지 않는다. 기존 기록이 없는 새 설치는 신규 로컬 이용 흐름으로 취급한다.

USDT는 1회 1,000 USDT, 현재 KRW 보상은 기존 10,000,000 KRW 정책을 유지하고 자동 환산하지 않는다. 별도 BTC 직접 보상 정책을 만들지 않으며 기존 KRW 충전 후 BTC를 매수하는 흐름을 유지한다. 광고를 닫았다는 사건만으로 지급하지 않고, 보상 획득과 잔고 저장이 완료된 뒤 충전 성공을 표시한다.

## 5. 시나리오 3: A 선물에서 BTC 롱을 연다

아래는 향후 USDT 선물 지원 시 광고 1회로 자금을 확보한 예시다. 계산 설명에서는 수수료·펀딩을 제외한다.

| 항목 | 예시 |
|---|---:|
| 계좌 | A 선물 / USDT |
| 광고 1회 충전 후 잔고 | 1,000 USDT |
| 진입 가격 | 100,000 USDT |
| 증거금 | 100 USDT |
| 레버리지 | 5배 |
| 명목금액 | 500 USDT |
| 수량 | 0.005 BTC |

주문 확인 화면에 `거래소 A · 선물 · BTC/USDT 무기한 · 롱`과 증거금·수수료·예상 청산가를 표시한다. 주문 직전 해당 계좌의 필요한 정산을 완료하고 최신 가격을 확인해 즉시 모의체결한다. 실제 호가 대기열을 복제한다는 의미는 아니며 체결 가격·슬리피지 규칙은 따로 정의한다.

가격·실제 수량·시각·증거금·체결 레버리지·규칙 버전과 고유 주문 ID를 저장한다. A 선물의 주문 가능 잔고와 포지션 담보에만 증거금·비용 정책을 반영한다. 비용을 어디서 차감할지는 작업 계획의 v1 제안을 기준으로 확정하고 이중 차감하지 않는다. 보유 포지션은 `계좌 + 계약` 단위로 구분한다. 초기에는 그 단위에서 롱/숏 동시 보유를 허용하지 않는다.

이 예시에서 가격이 101,000 USDT가 되면 손익은 0.005 × 1,000 = +5 USDT, 증거금 대비 ROE는 +5%다. 수량에 이미 5배 효과가 들어 있으므로 손익에 5를 다시 곱하지 않는다. 주문 화면을 10배로 바꾸거나 앱을 다시 실행해도 이미 체결한 포지션은 5배 기록을 유지한다.

## 6. 시나리오 4: B 거래소로 전환해 별도로 거래한다

A 선물의 BTC 롱이 열린 상태에서 B를 선택한다.

- A 포지션은 종료되지 않고 A 계좌에 남는다.
- B에서 선택한 현물/선물의 잔고와 상품을 표시한다.
- B 선물에서 BTC 숏을 열어도 A의 BTC 롱과 상계하거나 합치지 않는다.
- A의 미실현이익을 B의 주문 가능 잔고로 사용할 수 없다.
- 같은 BTC/USDT라도 체결가·Mark Price·펀딩·계약 규칙은 거래소별로 구분한다.

지원하지 않는 모드로 전환하면 주문 화면을 활성화하지 않는다. 화면 전환 전에 시작한 API 응답이 나중에 도착하더라도 이전 거래소의 가격으로 새 화면을 덮어쓰지 않는다.

## 7. 시나리오 5: 앱 사용 중 포지션을 확인한다

현재 화면의 거래소·상품에 맞는 시세로 차트와 평가손익을 갱신한다. 체결가격과 청산용 Mark Price를 구분한다.

열린 선물 포지션이 있는 거래소·계약의 위험 감시는 화면의 선택 상태와 분리한다. 탭을 현물로 바꾸었다고 기존 선물 포지션의 감시 상태를 유실하지 않는다. 필요한 계약만 구독하며 모든 거래소의 모든 종목을 미리 구독하지 않는다.

연결이 끊기거나 앱이 백그라운드로 이동해 연속 관측을 보장할 수 없는 구간은 재접속 정산 대상이다. 단순히 마지막 수신 가격의 시각을 마지막으로 연속 검증된 시각으로 간주하지 않는다.

## 8. 시나리오 6: 앱 종료 후 다시 진입한다

앱이 꺼진 동안에는 청산·펀딩 계산을 실행하지 않는다. 다음 접속에서 각 계좌가 보유한 포지션의 미정산 구간을 확인한다.

1. 로컬 기록의 스키마·미완료 커밋을 확인하고 마지막 정상 상태를 읽는다. 읽기 실패를 빈 계좌로 덮지 않는다.
2. 기존 자산을 마지막 확인 시각과 함께 표시한다. 현물은 현재 시세로 평가하고, 선물은 열린 포지션과 미완료 정산을 찾는다. 현물 시세 실패 시 보유 수량·취득 원가를 보존한다.
3. 현재 보고 있는 선물 계좌를 우선 처리하고 나머지는 제한된 동시성으로 처리한다. 전체 자산 화면이면 집계 대상 계좌들을 처리한다.
4. 거래소·계약·가격 종류별로 필요한 과거 데이터를 요청한다. 같은 범위는 재사용하되 다른 거래소의 가격은 섞지 않는다.
5. 마지막 검증 시각 이후의 가격과 펀딩 사건을 시간순으로 재생한다.
6. 최초 청산이 발생하면 그 이후의 펀딩이나 사용자 종료를 실행하지 않는다.
7. 계좌 변경·원장·정산 체크포인트를 로컬에 원자적으로 저장하고 확정 자산과 거래 가능 상태를 표시한다. 실패하면 이전 확정 상태를 유지한다.

| 계좌 | 미접속 기간 사건 | 결과 |
|---|---|---|
| A 현물 | 가격 하락 | 현재 평가액 갱신, 선물 청산 로직 적용 안 함 |
| A 선물 | Mark Price가 청산 조건 도달 후 회복 | 과거 청산 반영, 포지션 종료 |
| B 선물 | 청산 없음, 펀딩 지급 시각 통과 | 포지션 유지, B 펀딩 반영 |
| C 선물 | 데이터 조회 실패 | C만 정산 확인 중 |

미정산 계좌의 새 거래는 잠시 제한한다. C 정산 실패 때문에 A 현물이나 정산이 완료된 B 선물까지 막지 않는다. 정산은 차트에서 현재 선택한 거래소만 확인하는 방식으로 구현하지 않는다.

앱 시작·foreground·재연결이 겹쳐도 동일 정산을 중복 실행하지 않는다. 재생 중 도착한 현재가는 미검증 과거 구간을 건너뛰는 근거가 되지 않는다. 지금 받은 광고 보상으로 미접속 중의 청산을 되돌리지 않으며, v1에서는 가용 잔고 충전이 기존 포지션 담보를 자동 보충하지 않는다.

## 9. 시나리오 7: 사용자가 포지션을 종료한다

1. 종료 대상의 거래소·선물 계좌·계약을 고정한다.
2. 해당 포지션의 누락 가격과 펀딩을 먼저 확인한다.
3. 이미 청산된 상태면 사용자 종료를 체결하지 않고 청산 내역을 보여준다.
4. 살아 있는 포지션이면 해당 거래소의 최신 유효 가격으로 모의 전량 종료한다.
5. 남은 증거금과 실현손익·비용을 같은 선물 계좌에 반영한다.

요청 도중 거래소를 바꾸어도 접수한 주문의 계좌는 바뀌지 않는다. 완료 알림에도 거래소와 거래 유형을 표시한다. 통신 재시도는 같은 주문 ID로 처리해 중복 체결을 막는다.

## 10. 시나리오 8: 투자내역과 PNL을 확인한다

기본 범위는 `선택 거래소 + 현물/선물`이다.

| 화면 | 표시 내용 |
|---|---|
| A 현물 | A의 현물 잔고·보유 코인·매매손익 |
| A 선물 | A의 선물 잔고·포지션 증거금·포지션·실현/미실현손익·펀딩·청산 |
| B 선물 | B의 독립적인 선물 자산과 내역 |
| 전체 요약(선택 기능) | 거래소·현물/선물별 소계와 정산 상태 |

현물 보유 자산과 선물 포지션의 명목금액을 더해 총자산으로 표시하면 안 된다. 선물 계좌 자산은 주문 가능 잔액·예약/포지션 담보·미실현손익을 중복 없이 반영한다. 펀딩과 이미 낸 수수료를 잔액과 손익에서 이중 차감하지 않는다.

원화·BTC·USDT 금액을 그대로 합산하지 않는다. 첫 버전은 통화별 소계로 보여주고, 공통 통화 합계가 필요하면 환산 출처·기준 시각을 정의한다. 미정산 계좌가 있으면 전체 합계를 확정값처럼 표시하지 않는다. 수익률도 계좌별 수익률을 단순 평균하지 않는다.

최초 업비트 현물 지급과 광고 충전은 투자 수익으로 기록하지 않는다. 충전 직후 잔고가 증가해도 매매 PNL이 증가하지 않는다. 기존 현물 PNL은 보존하고 신규 선물 원장은 현물과 분리한다.

## 11. 시나리오를 지키기 위한 데이터 식별

```text
계좌 = 현재 로컬 데이터 영역 안의 거래소 + 거래유형 + 결제통화
상품 = 거래소 + 상품유형(현물/무기한 등) + 원본심볼 + 결제통화
포지션 = 계좌 + 상품 + 고유 포지션 ID
거래 사건 = 고유 사건 ID + 계좌 + 주문/포지션 + 발생시각/구간 + 기록시각
정산 진행 = 포지션/계좌 + 연속 검증 완료시각 + 처리 사건 키 + revision
```

`거래소 + 심볼`만으로는 같은 거래소의 BTCUSDT 현물과 무기한 계약을 구분하지 못한다. 반면 기존 현물의 ExchangePairID를 전체적으로 바꾸는 것은 별도 이관 작업이므로, 새 선물 모델과 통합 조회 경계부터 식별을 확장한다.

기존 코드 근거:

- `Mobit/Domain/Model/ExchangeModels.swift`: Exchange, SettlementCurrency, ExchangePairID. 현재 pair ID는 거래소와 원본 마켓 코드 조합이다.
- `Mobit/Common/ExchangeSelectionStore.swift`: 현재 거래소 선택만 저장한다. 거래소별 마지막 거래 유형은 추가 설계 대상이다.
- `Mobit/Data/Exchange/ExchangeMarketDataProvider.swift`: 실제 어댑터 구현·지원 여부를 확인해야 한다. enum 존재 자체로 연동 완료를 판단하지 않는다.
- `Mobit/Common/UserDataManager.swift`: 기존 현물 저장을 보존한다.

주문 요청에는 선택한 계좌와 상품을 명시적으로 담는다. 비동기 작업 중 전역의 현재 거래소 값을 다시 읽어 거래 대상을 결정하지 않는다. 시세 캐시·조회 결과·구독도 같은 범위로 분리한다.

- iOS: 가격 조회, 시세 구독, 정산 계산, 로컬 원장·자산 저장, 화면 상태.

- 주문·광고·정산의 읽기-계산-저장을 단일 변경 경로로 직렬화한다. 공유 저장소 전체의 원자 커밋과 revision 검증으로 오래된 응답의 덮어쓰기를 막는다. getter/setter 각각의 잠금만으로 충분하다고 판단하지 않는다.
- 앱 삭제·기기 변경 시 개인 데이터가 유지되지 않는 정책을 안내한다. OS 백업·기기 이전·오프로드는 별도 경로이므로 저장 위치와 백업 설정을 검증한다. 이 정책을 구현하기 위해 영구 사용자 식별자를 만들지 않는다.
- 시세가 없으면 다른 거래소 가격으로 체결하지 않는다. 오래된 가격은 마지막 확인값으로만 표시한다.
- 저장 실패를 성공으로 표시하지 않는다. 앱 종료 후 재개할 수 있는 미완료 요청 기록과 중복 방지 키를 둔다.
- 매매 timestamp뿐 아니라 가격·수량·방향·증거금·체결 레버리지·규칙 버전·수수료·펀딩 이력을 기록한다.
- 0 나눗셈·null·파싱 실패·비정상 수치·저장 실패는 명시적인 오류로 처리하고 이전 자산을 유지한다. 실패한 값을 0으로 바꿔 잔고·보유 수량을 저장하지 않는다.

부분 봉에는 해결되지 않은 정보 한계가 있다. 진입 12:00:40 이전/이후 중 언제 저가가 발생했는지 1분봉만으로 알 수 없다. 같은 봉의 손절·익절·청산 순서도 마찬가지다. 더 세밀한 동일 가격 종류의 자료를 확보할지, 공개된 모의 판정 규칙을 적용할지는 구현 전 결정해야 한다. 계속 보류할 수밖에 없는 자료 부족에 대해 확정적인 청산 사실을 만들어내지 않는다. 이 문서는 완전한 거래소 재현을 보장하지 않는다.

필수 확인 항목:

- A 선물 BTC 롱과 B 선물 BTC 숏이 합쳐지지 않는다.
- 거래소·거래 유형을 빠르게 전환해도 이전 응답이 새 화면을 덮지 않는다.
- 같은 요청을 반복해도 최초 자금·체결·펀딩이 중복되지 않는다.
- 미접속 중 청산 후 회복한 포지션이 살아 있는 것으로 표시되지 않는다.
- 재접속 시 숨겨진 거래소의 열린 포지션도 정산 대상에 포함된다.
- 한 거래소의 장애가 독립된 다른 계좌의 거래를 막지 않는다.
- 미정산 계좌가 포함된 전체 자산을 확정값으로 표시하지 않는다.
- 현물 기존 기록과 손익 계산이 보존된다.
- 광고·주문·재접속 정산이 겹쳐도 자금 유실이나 이중 반영이 없다.
- 0/null/비정상 가격·레버리지·저장 실패가 기존 자산 초기화로 이어지지 않는다.
- 앱 재실행·레버리지 선택 변경 후에도 기존 포지션은 실제 체결 레버리지로 계산된다.
- 미지원 선물 상품이 다른 거래소 어댑터로 조용히 연결되지 않는다.

이전 매분 함수 실행을 전제로 한 호출량·일정 추정은 현재 안의 견적으로 사용하지 않는다. 개인 계좌 저장을 위해 Supabase 요금제 결제를 전제하지 않는다. 선택적 공용 데이터 서비스를 도입할 때만 실제 조회량·저장량을 기준으로 비용을 별도 검토한다. 이 문서는 사용자 시나리오를 설명한다. 2026-09-22 시작한 코드 구현의 실제 완료 범위와 검증 결과는 작업 계획서 13절을 참조한다. 원격 서비스는 도입하지 않았다.

## 2026-09-29 사용자 정정: 국내 현물 시세 기반 선물 모의거래

확정 범위:

- 현재 앱 지원 거래소: 업비트·빗썸. 해당 거래소의 현물 공개 시세만 읽어 앱 안에서 롱/숏·레버리지·손익·청산을 시뮬레이션한다. Private 주문 API나 실제 선물 거래를 사용하지 않는다.
- 해외 거래소 Binance·OKX·Bybit는 추후 추가한다. 기존 Binance 구현은 현재 기능의 실행 경로에서 제외하며 기존 파일/테스트/저장 자료는 임의 삭제하지 않는다.
- KRW/BTC 마켓을 대상으로 시장 가격과 계좌 담보 통화를 구분한다. USDT 1,000 광고 보상은 미래 정책으로 유지한다. 계산기·저장소·주문 검증은 국내 KRW/BTC 계좌를 처리하도록 수정했다. 국내 시세 API 및 UI 연결은 아직 완료하지 않았다.
- 해외 Mark Price와 펀딩 자료는 국내 모의거래의 필수 조건이 아니다. 청산 기준은 선택한 국내 거래소/현물 종목의 가격이다. 펀딩을 적용할지는 별도 MOBIT 정책이며 임의로 해외 펀딩을 부과하지 않는다.

timestamp 기반 과거 검증:

1. 실제 진입 시각(ms), 대상 거래소/원본 마켓, 체결가·수량·레버리지를 보존한다.
2. 진입 경계 구간은 해당 거래소의 초봉 또는 공개 체결 이력을 조회해 진입 이후만 비교한다. 분봉에서 초봉을 생성하는 것이 아니라 별도 정밀 자료를 조회하는 것이다.
3. 업비트는 `/v1/candles/seconds`를 제공한다. 공식 문서 기준 최근 3개월, 요청당 최대 200개이며 무체결 초에는 봉이 없다. 따라서 기존 Binance의 연속 1분봉 개수 검사를 국내 초봉에 그대로 적용하면 안 된다.
4. 12:31:34.500 진입처럼 초 중간에 진입하면 34초 봉에도 진입 전 거래가 섞일 수 있다. 가능한 범위에서 ms timestamp가 있는 체결 이력으로 추가 판정한다. 동일 timestamp의 사건 순서·조회 기간 제한은 별도 검증한다.
5. 빗썸은 공식 공개 체결 이력 API와 cursor를 경계 구간 복원에 사용한다. 공식 문서 기준 daysAgo 1~7일, 최대 500건이며 to는 KST다. 업비트 체결 조회는 days_ago와 UTC 기준이므로 같은 파라미터/시간대 처리를 공유하지 않는다. 공식 문서 목록에서 초봉 API는 확인하지 못했으므로 업비트와 동일한 초봉 기능을 가정하지 않는다.
6. 전체 분이 보유 기간에 포함되면 분봉 고저가로 검사하고, 임계값 도달 시 세부 자료로 최초 발생 범위를 좁힌다. API 조회 한도·역순/중복·기간 제한·무체결과 실패를 구분한다.
7. 사용자가 선택했던 첫 분 마감가 모의 규칙은 정밀 조회가 불가능하다는 잘못된 전제에서 제안됐다. 정밀 자료로 해결할 수 있는 구간에 이를 강제하지 않는다. 복원 불가능한 경계에 적용할 fallback의 정확한 범위는 재정리한다.

수정 작업 순서:

1. 해외 기본 제공자 연결 중단 및 지침/계획 범위 정정 (이번 반영).
2. 국내 계좌/통화·기초 현물 종목·모의 가격 출처 모델 정리. 기존 USDT 저장은 보존하고 국내 가격으로 재해석하지 않는다.
3. 업비트 초봉/체결, 빗썸 체결 이력 어댑터와 조회 한계 테스트 추가.
4. 국내 가격용 정산기로 경계 구간·무체결 구간을 처리하고 현재 구간과 주문 직전 검증 연결.
5. 국내 시세 기준 통합 검증 후 W8 UI 연결. 기존 해외 API 테스트 통과 수치를 국내 기능 검증 완료로 보고하지 않는다.

## 2026-09-29 후속 구현: 국내 계좌 기반 및 검증 시점 재개

사용자 확정 사항:

- 진입 timestamp는 변경하지 않는다. 마지막으로 빠짐없이 검증한 구간 끝을 별도의 `verifiedThrough`로 저장한다.
- 다음 앱 접속 시 진입일부터 다시 조회하지 않고 저장한 검증 경계부터 이어서 조회한다. 시간 구간은 `[start, endExclusive)`로 처리하여 경계 데이터를 누락하지 않는다.
- 접속 시각이나 요청 시각을 검증 완료 시각으로 기록하지 않는다. 정산 결과와 검증 시점은 같은 원자 저장에 포함한다. 실패한 구간은 재시도한다.

이번 구현:

- 업비트·빗썸 KRW/BTC 선물 모의계좌를 준비 상태로 등록했다. 국내 원본 마켓의 가격 표시 통화와 담보 통화가 일치하는 주문만 계산하며 암묵적 환산은 하지 않는다.
- 국내 `KRW-BTC`와 같은 마켓 형식을 검사하고 거래소/통화 혼합을 차단한다. 실제 상장 종목 여부 확인은 국내 API 연결 시 추가한다.
- 증거금·수량·진입 레버리지 기반 계산을 국내 통화에도 적용했다. 해외 USDT 저장 자료는 보존하며 국내 가격으로 재해석하지 않는다.
- 새 선물 계좌 초기 잔액은 0이다. 국내 KRW 선물 광고 보상은 기존 KRW 정책인 1,000만 원을 적용하며 동일 광고 보상 중복 지급을 막는다. 향후 USDT 보상 1,000 정책을 유지한다. BTC 보상 정책은 미정이므로 보상을 만들지 않았고 UI도 활성화하지 않았다.
- 국내 모의 펀딩 정책이 정해지기 전에는 국내 포지션에 펀딩 이벤트/금액을 반영하지 않는다.
- 주문 직전 검증한 가격과 저장하려는 실행 가격이 다르면 저장을 거부한다.
- 재접속 후 저장된 검증 경계부터 요청하는 흐름, 진입 정보 보존, 급락 후 회복에도 청산 처리, 저장 실패 시 기존 파일 보존을 테스트에 추가했다.

남은 작업:

1. 국내 시세 제공자: 업비트 분봉/초봉/체결, 빗썸 분봉/체결 API 및 페이지·기간 제한 검증.
2. 국내 정산: 무체결 구간과 진입/현재 구간 세부 검증. 기존 정산기는 연속된 완료 분봉만 처리하므로 국내 API를 곧바로 연결하면 안 된다.
3. 실제 시장 데이터로 통합 검증 후 국내 제공자를 앱 생명주기에 연결하고 W8 UI를 진행한다. 현재 `shared` 제공자는 비활성 상태다.
4. BTC 마켓의 실제 UI 자금 조달 정책과 모의 계약 한도/수수료를 연결한다. 테스트의 레버리지 상한·수량 단위는 검증용이며 최종 상품 정책이 아니다.


## 최신 확정 정책: KRW 전용 선물 및 청산 회계

이 절은 이전 KRW/BTC 선물 지원, 수수료, MMR 제안보다 우선한다.

- 업비트·빗썸 선물은 독립된 선물 KRW 잔액만 사용한다. 선물 화면에서는 BTC 탭을 제공하지 않는다. 현물 BTC 매수·BTC 마켓 사용 흐름은 유지하며 자산을 공유하거나 이체하지 않는다.
- 수수료·펀딩은 없다. MMR 0.5% 참고 공식은 채택하지 않고 증거금 소진 시 전액 손실 처리한다. 가용 잔액을 추가 차감하지 않는다.
- 현재 앱의 시장가 체결 방식은 유지한다.
- 최대 레버리지: BTC/ETH 100, SOL/XRP/ADA/AVAX/NEAR/SUI/DOGE/SHIB/LINK/UNI/AAVE/RNDR 50, 나머지 20. RNDR과 다른 심볼을 임의로 같은 등급으로 해석하지 않는다.
- 같은 거래소·마켓의 활성 포지션은 하나다. 동일 방향·동일 레버리지 추가 진입은 합산하고 다른 방향/레버리지는 거부한다. 수량 가중평균 진입가, 증거금, 수량, 청산가, ROE를 갱신한다. 최초 진입 timestamp와 개별 체결 이력은 보존한다.
- 추가 진입 시각 전까지 기존 조건으로 청산 검증을 완료한 뒤 합산한다. 합산된 조건을 과거 구간에 소급 적용하지 않는다.
- 세부 자료를 끝내 복원할 수 없는 진입 경계에 한해 마감가 모의 규칙을 사용한다. 일시적 네트워크 오류·임의의 데이터 누락에는 적용하지 않는다.
- 소급 청산은 수동 종료처럼 선물 거래 내역과 실현 PNL에 남기고 자산에 반영한다. 수동 종료와 청산은 종료 원인으로 구분한다. 실제 발생 구간과 앱 정산 시각을 별도로 보존한다.
- 평가 총자산은 가용 KRW와 활성 포지션 평가자산의 합계로 계산한다. 미실현 이익을 주문 가능 잔액에 자동 가산하지 않는다. 검증 중 평가값은 확정 정산과 구분한다.

이번 코드 반영 범위:

- 국내 신규 선물 계좌/주문은 KRW만 허용하고 종목별 레버리지 상한과 수수료 0을 강제한다.
- 기존 BTC 개발 데이터는 읽기·검증 호환성을 보존하며 신규 BTC 거래는 차단한다.
- 원자 저장된 청산 상태로부터 선물 거래 내역·실현 PNL·평가자산을 일관되게 산출하는 조회 모델을 추가한다. 별도 현물 PNL 저장소에 중복 기록하지 않는다.
- 청산 내역에는 방향·레버리지·수량·청산 기준가·손실·발생 구간·정산 시각을 제공한다. 캔들 최저/최고 가격은 청산 근거로 보존하되 그 가격까지의 초과 손실을 사용자에게 부과하지 않는다.

후속 구현:

1. 추가 진입 체결 이력 및 합산 저장, 수동 종료와 통합한 종료 원장.
2. 국내 실제 시세, 초봉/체결 경계 검증 및 제한적 마감가 fallback.
3. 실시간/앱 재진입 정산 연결, 선물 KRW 전용 화면과 내역·PNL·자산 UI 연결.

현재 조회 모델은 청산 및 최초 진입을 처리한다. 추가 진입/수동 종료의 저장과 UI까지 완료된 것으로 간주하지 않는다.


## UI 연결 전 최신 구현 상태 (2026-09-29)

국내 경계 검증, 동일 조건 추가 진입, 전량 수동 종료, 내역·PNL·평가 조회와 주문 UseCase를 구현했다. UI는 아직 연결하지 않았다. 진입/추가 진입의 체결 이력을 보존하며, 현재 분의 안전 판정은 주문 준비 증명으로 사용하고 장기 재개는 완료 분봉 체크포인트로 이어간다. 세부 자료의 보존 기간이 지난 진입 분에만 기록을 남기는 마감가 규칙을 적용한다. 조회 실패나 빗썸 체결 페이지 경계의 완전성을 확인할 수 없는 경우에는 보류한다. 상세 구현·제한·UI 연결 순서는 [에이전트 작업 계획의 최신 절](futures-agent-implementation-plan.md)을 따른다.


## 리뷰 반영 및 현재 UI 상태 (2026-10-02)

국내 선물 UI는 연결되어 있으며 거래소 화면의 자산 요약/보유 탭, 주문, 투자내역, PNL과 광고 충전은 같은 거래소의 선물 KRW 계좌를 따른다. 현물 자산은 포함하지 않는다. 첫 광고 충전 전에 계좌를 0원으로 준비하므로 투자내역·주문 화면 방문 순서에 의존하지 않는다. PNL 공유 이미지와 문구에는 거래소·선물·KRW 및 방향·레버리지를 함께 표시한다.

업비트에서 8일 뒤 복귀한 밀리초 진입은 초봉 보존 기간 안이면 진입 초의 불완전한 부분만 종가 규칙으로 보완하고, 이후 검증 가능한 초봉의 고가·저가는 청산 판정에 사용한다. 대체 구간을 기록하며 조회 오류는 종가 fallback으로 숨기지 않는다. 초봉까지 보존 기간이 지난 경우의 기존 진입 분 마감가 규칙은 유지한다.

이번 새 테스트·빌드 결과와 남은 실기기/실시세 검증은 [구현 계획의 2026-10-02 리뷰 반영 절](futures-agent-implementation-plan.md)을 따른다. 연결된 UI와 단위 테스트 통과만으로 전체 출시 검증이 끝났다고 간주하지 않는다.
